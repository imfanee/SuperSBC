# Decisions and assumptions

Every choice the specification left open, and the reason it was made. Numbered so they can be referenced from code comments (`D-07`).

## Platform

* **D-01 FreeSWITCH image: `safarov/freeswitch:1.10.12`.** The official SignalWire images require a personal access token to pull, which breaks "docker compose up on a clean machine". The safarov image is public, Alpine based, built from the 1.10.12 release, and ships `mod_lua`, `mod_curl`, `mod_json_cdr`, `mod_xml_curl`, `mod_event_socket`, `mod_sofia`, `mod_opus`, `mod_g729` (the FreeSWITCH pass-through G.729; transcoding G.729 needs a licensed codec, see D-30).
* **D-02 Lua to Go transport: `mod_curl` via `freeswitch.API():executeString("curl ...")`.** The image has no `lua-cjson` or `luasocket`. `mod_curl` is loaded, supports `post`, `content-type`, `timeout` and `connect-timeout` in seconds, and returns the response body. JSON is handled by a vendored copy of `rxi/json.lua` (MIT), stored as `freeswitch/scripts/sbc/json.lua`. Verified inside the container in M1.
* **D-03 Lua VM is Lua 5.2** (bundled with FreeSWITCH 1.10). `luacheck` runs with `std = "lua52"` plus the FreeSWITCH globals.
* **D-04 Gateway and ACL configuration are rendered to files by Go, not served by `mod_xml_curl`.** Reasons: FreeSWITCH boots and keeps working when the API is down, the rendered XML is visible on disk for debugging, and `sofia profile external-egress rescan` plus `reloadacl` are documented operations. The files live on a shared Docker volume mounted at `/etc/freeswitch/sip_profiles/external-egress/` and `/etc/freeswitch/autoload_configs/acl.conf.xml`. `mod_xml_curl` is kept loaded but unused so the roadmap item is a config change, not a rebuild.
* **D-05 Docker networking: one bridge network with static IPs** (`172.28.0.0/24`). This makes the e2e tests deterministic (customer containers have known source IPs). For production, `deploy/docker-compose.host.yml` switches FreeSWITCH to `network_mode: host`; documented in OPERATIONS.md.
* **D-06 Ports.** Ingress profile 5060 (customers), egress profile 5080 (carriers), RTP 16384 to 32768 (each call uses two RTP sessions, so the range bounds concurrent calls at about 4000), Admin API 8080, internal API 8081 (docker network only), ESL 8021 (docker network only), Web UI 3000.

## Go

* **D-07 Router: `chi`.** It is stdlib `net/http` compatible, so handlers are plain functions, middleware composes cleanly, and it has no framework lock-in. gin would have forced its own context type into every handler.
* **D-08 SQL: `pgx/v5` directly with hand-written queries in `internal/store`.** `sqlc` was considered; it adds a code generation step and does not model the dynamic filters that CDR search and reports need. All queries are parameterised. Integration tests run against a real Postgres.
* **D-09 Migrations: `goose` embedded in the binary**, run automatically at API start (`SBC_AUTO_MIGRATE=true` by default; set false in multi-node production and run `sbc-api migrate` once).
* **D-10 Money: `shopspring/decimal`** in Go, `NUMERIC(18,6)` in Postgres, strings in JSON. Rounding is half-up to 6 decimal places: `decimal.Round(6)` rounds half away from zero, which is half-up for positive amounts, and negative amounts are only ever produced by negating a rounded positive.
* **D-11 Redis client: `redis/go-redis/v9`.**
* **D-12 ESL client: in-house minimal implementation (`internal/esl`).** The protocol is simple (auth, `api`, `bgapi`, `event plain`). The third-party libraries are either unmaintained or drag in more than needed. It supports reconnect with backoff.
* **D-13 Logging: `log/slog` JSON** to stdout. Every log line inside a call carries `call_uuid`. Lua logs through `freeswitch.consoleLog` with a `[sbc uuid=...]` prefix, and FreeSWITCH is configured to log JSON-ish key=value so `docs/OPERATIONS.md` can show one `grep` that stitches all three.
* **D-14 OpenAPI 3.1: `swaggo/swag` v2 with `--v3.1`**, generated from handler annotations at build time into `docs/API.md` and served at `/api/docs`.
* **D-15 Auth: argon2id (`golang.org/x/crypto/argon2`), JWT (`golang-jwt/jwt/v5`) in httpOnly cookies, CSRF double-submit cookie, TOTP via `pquerna/otp`.**
* **D-16 The `setup` endpoint.** Lua makes one `POST /internal/v1/call/setup` that performs authorise, normalise, sell rate, balance check, reserve, route and buy rate lookups. Each is a separate Go function with the semantics of Section 3, and each also has its own endpoint for tooling and tests.
* **D-17 Idempotency of billing** is guarded by `cdrs.billed_at` under `SELECT ... FOR UPDATE`, not by a separate table.

## Billing semantics

* **D-18 Reservation amount** = `Amount(BilledSeconds(reserve_minutes*60, rate...), rate)` i.e. 5 minutes rated with the same increment rules, plus connect fee. For a 60/60 rate at 0.02 this is 0.10.
* **D-19 Available balance must be `> 0` and `>= reserve_amount`.** Both conditions are checked; with a positive reservation the second implies the first, but the first is kept explicit so a rate of 0.000000 per minute (free destination) still requires a non-negative account.
* **D-20 `max_call_seconds = floor(available_after_reservation_plus_reservation / rate_per_second)`**, capped by `billing.max_call_duration` (4 h). The reservation itself is part of what the customer may spend, so `available + reserve_amount` is the spendable amount. If `rate_per_min` is 0, `max_call_seconds` is the cap.
* **D-21 Overrun edge.** The true-up may exceed `max_call_seconds` money by at most one `subsequent_increment` (because `sched_hangup` fires at second granularity and rounding goes up). This can push `balance + allowed_credit` below zero by at most one increment. Documented in BILLING.md; not "fixed" because the alternative (hanging up one increment early) short-changes the customer.
* **D-22 Carrier accounts are liabilities.** `balance` on a carrier account represents prepaid deposit with the supplier (positive) or what we owe (negative). `cost` entries decrement it; `topup` records a payment to the supplier.
* **D-23 Failed attempts cost 0.** `carriers.charge_failed_attempts` exists as a column, defaults false, and is not yet honoured (roadmap).
* **D-24 Currency.** Everything defaults to USD. `fx_rates` and conversion at rating time arrive in M4; until then, a rate group, its customers and carriers are assumed to share a currency and the API refuses to attach a rate group with a different currency.

## Call handling

* **D-25 Source address** is taken from `sip_network_ip` / `sip_network_port` (the UDP/TCP peer), never from Via or Contact.
* **D-26 Number normalisation** (Section 3 Step 2) in order: strip `tech_prefix` if the number starts with it; drop everything except digits and a leading `+`; `+CC...` becomes `CC...`; `00CC...` becomes `CC...` (international prefix configurable per customer later, default `00`); `011` is NOT treated as international by default (US customers set `intl_prefix=011` on the customer in a later milestone, see ROADMAP); if the result starts with `0` and `default_country_code` is set, the leading `0` is dropped and the country code prepended; a number without a leading 0 and shorter than 7 digits is malformed; numbers longer than 15 digits are malformed.
* **D-27 Reason phrases** are sent with the `respond` dialplan application before the channel is answered, so the exact text from Section 3 reaches the customer.
* **D-28 Relaying carrier codes.** After a failed bridge the a-leg reads `last_bridge_proto_specific_hangup_cause` (`sip:503`) and responds with that code and the standard reason phrase for it. If the b-leg failed without a SIP code (timeout, gateway down) the FreeSWITCH cause is mapped through the standard FreeSWITCH cause to SIP code table.
* **D-29 PDD** is measured in Lua from the moment the bridge is started to the a-leg's `progress_uepoch` (first 18x relayed) or `answer_uepoch`, whichever comes first, per attempt. If an earlier attempt already produced early media the later attempt's PDD is measured to answer only. Good enough for reports; exact per-leg timing is a roadmap item using `uuid_dump` on the b-leg.
* **D-30 Codecs.** Default allowed list `PCMA,PCMU,OPUS,G722`. `G729` is accepted in lists; with the stock `mod_g729` FreeSWITCH can pass it through but not transcode it. Documented in OPERATIONS.md.
* **D-31 Concurrency limits** use Redis `INCR` with a key per customer that is decremented on hangup and reconciled every minute from `active_calls`. CPS uses a fixed one-second window counter (`cps:<customer>:<unix_second>`, TTL 2 s), which is a token bucket with refill equal to capacity every second: simple, and what carriers mean by "CPS".
* **D-32 Circuit breaker** state is kept in Redis so two API nodes agree. Thresholds: 20 consecutive carrier faults, or ASR < 10 % over the last 5 minutes with at least 50 attempts, degrade for 60 s.
* **D-33 Session timers**: `enable-timer=true`, `session-timeout=1800`, `minimum-session-expires=120` on both profiles.
* **D-34 RTP timeout**: `rtp-timeout-sec=300`, `rtp-hold-timeout-sec=1800`.
* **D-35 Max call duration** default 4 h, enforced twice: `sched_hangup` (FreeSWITCH) and the reservation TTL (reconciliation).
* **D-36 CDR row is created at setup**, before dialling, with `disposition = 'pending'`, so a crash mid-call still leaves a row for reconciliation. `pending` is an internal state; the API never reports it to reports (they filter it out) and the reconciliation worker resolves it.
* **D-37 `sbc_node`** is the hostname of the API instance that billed the call.

## Testing

* **D-38 Unit tests** for every pure package (`rating`, `numbering`, `prefix`, `failover`). **Integration tests** (`//go:build integration`) need `SBC_TEST_DATABASE_URL` and `SBC_TEST_REDIS_URL`, provided by `make test-integration` through compose. **E2E tests** are Go tests (`tests/e2e`, build tag `e2e`) that drive `sipp` containers with `docker compose run` and assert against the Admin API and Postgres.
* **D-39 Mock carriers are sipp UAS containers** with three scenarios: `uas_answer.xml` (180, 200, waits for BYE), `uas_503.xml`, `uas_404.xml`. Routes in the seed data point different prefixes at different combinations so every e2e scenario in M1 is a plain call to a known number. sipp UAS scenarios do not answer out-of-dialog OPTIONS (they abort the pseudo-call), so the demo carriers are seeded with `sip_options_ping = false`; real carriers keep the default `true`. Gateway DOWN handling is exercised by pointing a carrier at an unreachable host in the M2 tests.
* **D-40 Seed data** is loaded by `sbc-api seed` (idempotent, keyed by name): customers `acme` (172.28.0.101, balance 10.00) and `beta` (172.28.0.102, balance 0.00), carriers `carrier-answer`, `carrier-503`, `carrier-404`, selling deck `retail-usd`, buying decks per carrier, route group `default`.

## Style

* **D-43 ANI is the From user.** Customer supplied `P-Asserted-Identity` and `Remote-Party-ID` headers are ignored for caller identification and never forwarded (FreeSWITCH would otherwise prefer them as caller id). A per-customer "trust PAI" flag is on the roadmap together with Privacy handling.

* **D-44 Blocked destinations answer `403 Destination blocked`** (disposition `rejected_route`, step `blocklist`). The specification does not name a code for block lists; 403 is what carriers conventionally send for barred destinations. The per-customer list is checked before the global blacklist; `customers.blocked_prefixes_enabled=false` exempts a customer from both.
* **D-45 Multi-currency.** Every account has a currency; every rate deck has a currency. At setup the selling rate is converted from the deck currency to the customer's account currency with the latest `fx_rates` row (inverse pairs are used when only the reverse direction exists) and the multiplier is stored in `cdrs.sell_fx` so billing reproduces exactly the same price. The buying rate is converted at billing time into the carrier's account currency (`cdrs.buy_fx`); a rate that changed between setup and hangup therefore costs at the hangup rate, which is the normal wholesale convention. A missing exchange rate rejects the call with `404 No rate for destination` (sell side) or costs at 1:1 with an error log (buy side). `margin` is only meaningful when both currencies match; reports show the currencies next to the money.

* **D-46 Web stack versions.** React 18.3 as specified (the Vite template defaults to 19; both work with the code), Vite 7, TypeScript 5.9, Tailwind CSS 4 with the `@tailwindcss/vite` plugin, shadcn/ui components written into `web/src/components/ui` by hand on Radix primitives (the shadcn CLI needs interactive prompts and vendors more than we use), TanStack Query 5, TanStack Table 8, React Router 7, react-hook-form 7 with zod 4, Recharts 3, sonner, next-themes. The build stage uses `node:22-bookworm-slim` because the npm lockfile generated on glibc omits the musl rollup binary. Money is displayed at 4 decimals (`lib/utils.money`), never rounded anywhere else.
* **D-47 Password reset without email.** SuperSBC sends no email. An admin generates a one-time reset link (`POST /users/{id}/reset-token`, valid one hour) and hands it to the user; the forgot-password page explains this.

* **D-48 Reconciliation sweep.** With FreeSWITCH reachable, any reservation older than `orphan_timeout` whose channel is absent from `show channels` is released, not only those past `max_call_duration + orphan_timeout`; the channel list is authoritative, and this repairs an API restart that lost hangup events within minutes. Without FreeSWITCH the specification's timing applies.
* **D-49 Hourly roll-ups feed the dashboard only.** `cdr_hourly_stats` is recomputed every minute for the current and previous hour and for any hour whose CDRs changed; the dashboard's hourly profile reads it. All other reports query `cdrs` directly so any filter combination works; the roll-up is the fast path, not a second source of truth.
* **D-50 SIP trace scope.** Sofia traces a whole profile, not one address; the UI enables tracing on the ingress profile for N minutes (auto-off) and filters the captured messages by address when displaying them. The trace is captured in `freeswitch.log` because the logfile profile maps the `console` level.

* **D-51 Two stacks, one box.** Dev and live are separate compose projects with separate `.env` files, volumes and bridge subnets (172.28 and 172.29). Live FreeSWITCH uses `network_mode: host` (SIP and RTP need the real address), ESL listens on the live bridge gateway 172.29.0.1 so only containers reach it, the internal API is published on 127.0.0.1:8081 for FreeSWITCH, and nginx terminates TLS on 8443 with 8080 redirecting (secure cookies require HTTPS). Dev ports are bound to loopback so nothing from the dev stack is reachable from the internet. The host firewall is nftables in its own table so Docker's rules stay untouched.

* **D-41 No em-dash character anywhere.** Enforced by `make lint` (`grep` over the tree).
* **D-42 Conventional commits**, one per milestone, plus intermediate commits when a milestone is large.

## Section 7 SBC features (M5 features)

* **D-52 One policy step, two new rejections.** TLS and SRTP requirements are checked as a "policy" step right after authentication (before admission counters and rating): `require_tls` on a customer rejects UDP/TCP INVITEs with `403 TLS required`; `srtp_mode=mandatory` rejects an SDP without `a=crypto` (or `RTP/SAVP`) with `488 SRTP required`. Both write a `rejected_auth` CDR with `transport_in` and `srtp_in` so the reason is visible in the CDR list. `srtp_mode=optional` accepts both and sets `rtp_secure_media=optional`, `off` forces plain RTP.
* **D-53 TLS on both profiles from the same certificate.** `SBC_FS_TLS=true` enables `tls-sip-port` 5061 (ingress) and 5081 (egress) with the certificate directory `freeswitch/tls` (`agent.pem` = key plus certificate, `cafile.pem`) generated by `freeswitch/tls/gen.sh` (self-signed) or copied from a real certificate. `SBC_FS_TLS_VERIFY_POLICY` defaults to `none`: wholesale customers and carriers rarely present a client certificate and the address allow-list remains the authentication; `SBC_FS_TLS_VERSION` defaults to TLS 1.2 and 1.3. A customer's `customer_ips.transport=tls` filter plus `require_tls` is the per customer switch; a carrier is TLS when `carriers.transport=tls` (`;transport=tls` in the dial string, `srtp_mode` decides the media).
* **D-54 Privacy per carrier.** A call is "private" when the INVITE carries `Privacy: id|user|header` or an anonymous From user. `carriers.privacy_mode` decides what the carrier sees: `anonymize` (default) sends From `anonymous` with `origination_privacy=hide_name:hide_number` and `Privacy: id`; `pass` sends the real number in From and P-Asserted-Identity plus `Privacy: id` (trusted carriers that apply the restriction themselves); `ignore` sends the real identity without any Privacy header. The CDR keeps `caller_number` as the real ANI and `privacy=true`.
* **D-55 Header rule semantics.** `header_rules` rows belong to a customer or a carrier, have a direction (`egress`: INVITE to the carrier; `response`: responses to the customer), an action (`add` a fixed value with `{caller} {called} {customer} {carrier} {call_uuid} {node_ip}` placeholders, `passthrough` a customer header verbatim, `remove`) and a priority. Customer rules apply first, carrier rules override the same header, and a `remove` cancels any lower priority `add` or `passthrough` for the header. Rules are cached in the API (invalidated through `headers:changed`), rendered as `sip_h_` / `sip_rh_` variables and passthrough headers are read by Lua from `sip_h_<name>` of the a-leg. Identity headers (From, To, PAI, RPID, Privacy) are never passed through; use the privacy and trust_pai settings.
* **D-56 Media mode precedence.** `anchor` (relay and transcode), `smart` (see D-84), `proxy` (relay without transcoding) and `bypass` (SDP passed through, media direct between customer and carrier). The stricter of the customer's and the carrier's mode wins per attempt (anchor beats smart beats proxy beats bypass), so bypass only happens when both sides allow it. Bypass and proxy calls have no RTP statistics or SRTP flags in the CDR and cannot be transcoded; the media mode of each attempt is recorded in `cdrs.media_mode`.
* **D-57 DTMF interworking.** `dtmf_mode` on customers (a-leg) and carriers (b-leg): `rfc2833` (default), `info` and `inband`. Inband uses `dtmf_type=none` plus `start_dtmf` (detect tones in audio) and `start_dtmf_generate` (play tones) executed on answer; FreeSWITCH converts between the two legs' modes because media is anchored. Inband forces media anchoring on that leg.
* **D-58 Scanner bans.** Every `403 IP not authorized` increments `scan:<ip>` in Redis (window `SBC_BAN_WINDOW`, default 5 minutes); at `SBC_BAN_THRESHOLD` (20) the address is written to `banned_ips` for `SBC_BAN_DURATION` (1 hour), rendered into the customers ACL as a `deny` node after the allow nodes and `reloadacl` is issued, so Sofia answers `403 Forbidden` without reaching Lua or the API. A worker expires bans every minute; manual bans through the API can be permanent. The ban list is a per node protection; a host firewall set is the next line for volumetric floods.
* **D-59 100rel per profile.** `SBC_FS_INGRESS_100REL` and `SBC_FS_EGRESS_100REL` render `enable-100rel` on the profiles. Off by default (many wholesale carriers mis-handle PRACK); turning it on is a config change plus profile restart, not a per customer setting, because Sofia negotiates the extension per profile.
* **D-60 sipp 3.7 image.** The e2e suite builds `supersbc/sipp:3.7` from source (`tests/e2e/sipp/Dockerfile`) because the published 3.5.1 image cannot complete a TLS 1.2 handshake; all sipp services share the image.

## Roadmap items built after go-live

* **D-61 Routing windows.** `route_carriers.window` holds "days hh:mm-hh:mm [zone]" clauses separated by ";" (`mon-fri 08:00-18:00 Europe/London; sat,sun 00:00-24:00`); the end is exclusive, a range that ends before it starts wraps past midnight, an empty window is always open. The API rejects a window it cannot parse (400) so a typo never silently removes a carrier; at call time a closed window skips the carrier with reason `outside_window` (visible in the simulator). Evaluated per call in Go against the node clock, no cache to invalidate.
* **D-62 Failed attempt charging.** With `carriers.charge_failed_attempts` every attempt that did not answer costs the connect fee of the buy rate it was routed with (converted to the carrier account currency), posted as one `cost` ledger entry per attempt inside the same idempotent billing transaction, recorded on the attempt (`attempts[].cost`) and added to `cdrs.cost` so margins include it. A per-minute charge for failed attempts is not modelled: wholesale carriers that bill failed attempts bill a fixed fee.
* **D-63 Invoices are prepaid usage statements.** One `invoices` row per account and calendar month (UTC), numbered `INV-YYYYMM-nnnnnn` from a sequence, generated by an hourly worker for the previous month (every node may run it; the unique constraint makes it idempotent) or on demand for any past or current month through `POST /invoices/generate`. The row stores the ledger figures (opening, top-ups, charges or costs, adjustments, refunds, closing) and the answered usage per destination from the CDRs, so the PDF (`GET /invoices/{id}.pdf`, go-pdf/fpdf, no external service) can be re-rendered identically later. No tax is computed: prepaid wholesale invoices state usage against money already received; the issuer identity comes from `SBC_INVOICE_OPERATOR_NAME`, `SBC_INVOICE_OPERATOR_ADDRESS` (lines separated by `|`) and `SBC_INVOICE_FOOTER`. An invoice generated for the current month is a snapshot and can only be regenerated by deleting the row.
* **D-64 STIR/SHAKEN verification, not signing.** `customers.stir_mode` is `ignore` (default), `verify` (check and record) or `require` (reject). The verifier parses the Identity header (compact JWS, `ppt=shaken`, ES256), fetches the certificate from `x5u` (https only unless `SBC_STIR_ALLOW_HTTP`, cached one hour, failures cached one minute, 1.5 s fetch timeout so a slow STI-CR cannot stall call setup), checks the signature, the certificate dates, the chain when `SBC_STIR_CA_FILE` names a trusted root bundle, the `iat` freshness (`SBC_STIR_MAX_AGE`, 60 s) and that `orig.tn` and `dest.tn` match the normalised caller and called numbers. Rejections use the RFC 8224 codes: 428 Use Identity Header (missing), 436 Bad Identity Info (certificate unavailable), 438 Invalid Identity Header (bad signature, stale, mismatch). The status (`none`, `verified`, `stale`, `mismatch`, `no_cert`, `invalid`) and attestation level go into `cdrs.stir_status` / `stir_attest` and the `sbc_stir_verifications_total` metric. A verified Identity header is forwarded to the carrier (`SBC_STIR_FORWARD`, default on); signing our own PASSporTs (authentication service) needs an STI certificate from a policy administrator and is deliberately not built: without one the SBC can only pass attestations through. `stir.Sign` exists for tests and labs.
* **D-65 HEP capture is a FreeSWITCH setting, HOMER is optional.** `SBC_FS_HEP_SERVER` (`udp:host:9060;hep=3;capture_id=N`) renders `capture-server` in sofia.conf and `sip-capture=yes` on both profiles, so every SIP message of both legs is mirrored as HEPv3 (a restart of FreeSWITCH applies it). The dev stack mirrors to the docker bridge address 172.28.0.1 where the e2e suite listens; `make homer-up` starts heplify-server (bound to that address, so the live stack on the host network can point at it too), its own Postgres and the HOMER web UI on 127.0.0.1:19080 (admin / sipcapture, change it). HOMER is not part of the default stack: it is a third party product with its own retention (`HOMER_KEEP_DAYS`) and the built-in SIP trace covers the ad hoc case.
* **D-66 Packet level flood protection lives in the host firewall.** The ACL ban (D-58) stops calls but FreeSWITCH still parses every packet of a flood. The live nftables ruleset therefore (a) drops everything from the `banned` set, which `deploy/live/ban-sync.sh` fills from the ban list the API exports to `SBC_BAN_EXPORT_FILE` (one line per address with the seconds left, so nftables expires entries itself; a systemd timer runs it every 30 s), and (b) rate limits SIP per source with nftables meters: over 200 UDP packets per second (burst 400) to 5060, or over 30 new TCP connections per second to 5060/5061, is dropped. The limits are far above what a legitimate customer trunk sends (a 100 CPS trunk is under 100 packets per second) and far below a flood. The API never talks to nftables (it runs in a container without CAP_NET_ADMIN); the file hand-off keeps the privilege on the host script.
* **D-67 TLS client certificates are verified per profile, bound per customer through the subject list.** Sofia can verify the client certificate of an inbound TLS connection against `cafile.pem` (`tls-verify-policy=in`) and restrict the accepted subjects (`subjects_in` with `tls-verify-in-subjects`), but it does not expose the peer certificate to the dialplan, so a call cannot be attributed to a customer by certificate. The binding is therefore: `customers.tls_subject` (CN or SAN, several comma separated) is rendered by the API into `<fsconfig>/ingress/tls_subjects.xml`, included by the ingress profile; a connection must present a certificate that chains to `cafile.pem` (put the CA that issues customer certificates there, after our own chain) and whose subject is listed on an active customer, and the call is then attributed by source address as always (`require_tls` makes the address usable over TLS only). Changing the list needs a profile restart (`POST /system/profiles/external-ingress/restart`, drops the calls on that profile, so do it at a quiet time). The dev stack runs `subjects_in` with the self-signed certificate as its own CA; live defaults to `none` because most wholesale customers do not present client certificates.
* **D-68 Active-passive HA without shared call state.** Two boxes behind a keepalived VRRP address; FreeSWITCH binds the VIP on both (`ip_nonlocal_bind`), only the master receives traffic, and calls in progress on a failed box are lost (documented, not hidden). Everything stateful is shared: Postgres primary with a streaming replica (pgx multi-host URL with `target_session_attrs=read-write`; promotion is manual by design, Patroni or a managed service can automate it), Redis with Sentinel (`SBC_REDIS_SENTINEL_ADDRS`, go-redis failover client). Two multi node fixes were needed in the API: reservations record their node and the channel sweep is node scoped (a node must not release the money of a call alive on its peer), and all periodic workers were checked to be idempotent under concurrent execution. Details and set-up in docs/HA.md.
* **D-69 The firewall follows the database.** The host firewall's `customers`, `carriers` and `banned` sets are no longer edited by hand. `sbc-api` writes `firewall.json` (customer address blocks from `customer_ips`, carrier gateway hosts plus `carriers.signalling_sources`, bans with their remaining seconds) to the shared state directory on every change (the same trigger that re-renders the FreeSWITCH ACLs), and `sbc-fwsync`, a small Go program running on the host as a systemd service, polls the file every second, resolves carrier hostnames (again every five minutes), and replaces the three sets in one `nft -f` transaction whenever the result differs. It also writes `firewall-sets.nft`, which the ruleset includes **as a glob** (`state/*.nft`), so the sets are populated at boot before the containers start; a literal include would fail the whole ruleset when the file is missing or not yet readable, leaving a rebooted box with no firewall at all, while a glob that matches nothing loads the sets empty (deny by default) until sbc-fwsync fills them. `nftables.service` is ordered `After=local-fs.target` for the same reason. The split (export in the container, apply on the host) keeps `CAP_NET_ADMIN` out of the API container. With `customers` enforced at the kernel, SIP from an unknown address never reaches FreeSWITCH on a live box; the scanner ban logic remains for stacks that run without the host firewall. Replaces the ban-sync timer of D-66.
* **D-70 Password reset by e-mail, when SMTP is configured.** Supersedes the "no e-mail" stance of D-47. `SBC_SMTP_*` configures an outgoing server (STARTTLS on 587, implicit TLS on 465, or clear on 25 for a local relay); when a host is set, `POST /auth/forgot {email}` creates the same one hour, one time token an admin can create by hand and e-mails a link built from `SBC_PUBLIC_URL`. The endpoint always answers 202 (accounts are never confirmed or denied), shares the login throttle (10 requests per address in 15 minutes, 100 per source), sends asynchronously so SMTP latency does not delay the response, and is audited. Without SMTP the forgot page keeps pointing at the administrator generated link. Notifications (low balance) are still not e-mailed; that is a separate roadmap item.
* **D-71 Per call SIP trace from the HOMER capture store.** The capture pipeline of D-65 (FreeSWITCH HEPv3 to heplify-server to Postgres) is now part of the live stack (`hepdb`, `heplify`, always on, retention `HOMER_KEEP_DAYS`, default 30 days) rather than an optional profile, and the CDR detail links to a "SIP trace" page that opens in a new tab and shows every message of the call: both legs in time order, source and destination, method or status, and on expansion the full headers and body. The API (`GET /cdrs/{id}/sip`) reads the capture database directly (`SBC_HEP_DATABASE_URL`, lazily connected, so a stopped HOMER never blocks the API) and correlates legs without a shared Call-ID: the customer leg by the Call-ID now stored on the CDR (`cdrs.sip_call_id`, also a list filter), the carrier legs by the `X-SBC-Call: <call uuid>` header the SBC sends on every INVITE, then all messages sharing those Call-IDs in the call's time window. The HOMER web UI stays optional (`--profile homer`); the SBC's own viewer is enough for the "what happened to this call" question and needs no second login. The viewer also exports pcap (customer leg, carrier leg or the whole call): the SIP payload is written byte for byte as FreeSWITCH saw it on the wire (decrypted for TLS) with the real addresses, ports, transport and HEP capture timestamps; layer 2 and 3 headers are synthesised (HEP carries none), TCP segments get consistent sequence numbers so Wireshark reassembles them, and UDP checksums are left at zero. Wireshark dissects port 5060 as SIP; for 5061/5081 use "Decode As".
* **D-72 Invoice ledger apart from the call ledger.** The prepaid call ledger (balance, reservations, charges, top-ups) is untouched; a second, accounts-receivable view records what was invoiced and what was received against it. Invoices may now cover a calendar month or a custom period (`from`/`to`, kind `custom`); periods of one account never overlap (409), so every call is invoiced exactly once, and the monthly worker skips a month a custom invoice already covers. Each invoice carries `amount` (the usage of the period: charges for a customer, costs for a carrier) and derives `paid`/`status` (open, partial, paid, overpaid, nothing_due) from its allocations. A payment (`invoice_payments`: amount, date, reference, method, notes) is allocated to invoices (`invoice_allocations`): by hand to one or several invoices, fully or partially, or automatically to open invoices oldest first, with any remainder kept as an unallocated credit; allocations can never exceed the payment or what an invoice still owes. Recording a payment optionally posts the same amount to the call ledger as a top-up (default on for customers), and the two entries reference each other, so a customer's prepayment is one operation while the two ledgers stay separately auditable. Payments are not deletable through the API (record a correcting entry instead; the audit log has the history). The PDF lists the payments applied and the balance due.
* **D-73 Routing modes.** A route group combines four switches. *Least cost* (existing) orders by buy rate. *Lossless* drops, per call, every carrier whose buy rate exceeds the customer's sell rate for that number (`lossless_skipped` in the simulator); it is a per group policy next to the system wide `SBC_ROUTING_BLOCK_NEGATIVE_MARGIN`. *Quality based* orders by a measured score, best first. *Percentage based* draws the first carrier at random with probability equal to its share (the weight column, read as percent; zero means failover only) and lists the others by descending share as the failover chain, so the distribution converges to the shares while every carrier stays reachable; it is exclusive because a fixed distribution contradicts the other three orderings (enforced by a database constraint and the API). The sort key when quality or LCR are on is `(quality tier desc, buy rate asc, priority asc)` with the weighted shuffle inside equal keys, so LCR decides inside a quality tier and priority breaks ties; degraded carriers (breaker) go last in every mode.

  The quality score is per carrier and **route prefix** (the routing table entry that matched, so the key space is routes times carriers, not dialled numbers): every attempt result increments an hourly Redis hash (attempts, answered, reached, faults, PDD) with one pipelined command group, the same cost as the existing circuit breaker and no database write. A background refresh (`SBC_QUALITY_REFRESH`, 30 s) recomputes all scores from the last `SBC_QUALITY_WINDOW_HOURS` (24) buckets with exponential decay (factor 0.85 per hour) and keeps them in memory; the call path reads a map. `score = 0.5 ASR + 0.3 NER + 0.2 (1 - PDD/8 s) - 0.2 fault ratio`, rounded to tiers of 0.05 so noise does not reorder carriers on every call. A prefix with fewer than `SBC_QUALITY_MIN_SAMPLES` (20) attempts falls back to the carrier wide score, then to a neutral 0.5, so new carriers are neither favoured nor punished. Scores are visible in the route preview, the simulator and `GET /carriers/{id}/quality`.
* **D-74 Column layout is a browser preference.** The CDR table's Columns menu hides, shows and reorders columns; both choices are stored in `localStorage` per browser rather than per user in the database, because they are viewing preferences, not configuration (no server round trip, no migration, nothing to reconcile between nodes), and they degrade to the default layout when storage is unavailable. The last visible column cannot be hidden, and a stored order that does not mention a column (one added by a later release) keeps that column after the ones it lists, so an upgrade never hides new data. Visibility and order are props of the shared `DataTable`, and the menu plus its storage live in one `useColumnPrefs` hook keyed per table (`sbc.cdr`, `sbc.live-calls`), so another table adopts them in two lines and keeps its own layout.
* **D-75 Several endpoints per carrier.** A carrier is no longer one address: `carrier_endpoints` holds its signalling addresses (host, port, transport, priority, weight, enabled) and each one is rendered as its own FreeSWITCH gateway, named `<carrier>` when there is a single endpoint and `<carrier>-ep<seq>` when there are several (mod_sofia silently refuses gateway names containing punctuation such as `#`, so the suffix stays alphanumeric). Existing carriers were migrated to a one endpoint list and keep their gateway name, so nothing churns; `carriers.gateway_host/port/transport` stay as the mirror of the primary endpoint for the UI, the firewall export and the plain carrier API.

  Routing expands each chosen carrier into its usable endpoints, keeping them adjacent in the dial list, so Lua's existing bridge loop fails over inside a carrier before moving to the next carrier; `SBC_ROUTING_MAX_ENDPOINTS_PER_CARRIER` (3) bounds how many addresses one call may try. `carriers.endpoint_lb` picks the order: `failover` (priority, weighted random inside a priority), `round_robin` (equal shares) or `weighted` (by the endpoint weight); in all three the remaining endpoints stay behind the first as failover. Every attempt records the address it used (`attempts[].endpoint`).

  Health has two sources. With OPTIONS ping on, FreeSWITCH decides and the gateway poller reports per endpoint, which is the accurate option and the default. Carriers that do not answer OPTIONS can instead enable `endpoint_park_on_failure`: attempts that never reach the far end count against the address and `endpoint_fail_threshold` (2) of them in a row park it in Redis for `endpoint_retry_seconds` (300), after which it is tried again; an answered call or a rejection by the far end clears the counter, and an operator can revive an address at once. That path is opt in because FreeSWITCH reports a carrier answering `503 Service Unavailable` exactly like an address that answers nothing (same hangup cause and protocol cause), so a carrier that sheds load with 503 would otherwise be parked; where that distinction matters, use OPTIONS ping.
* **D-76 Area codes label every call.** `area_codes` maps a country code plus an area code to a description and an operator (`243` + `81` is Vodacom, `91` + `22` is Mumbai), matched longest prefix first against the normalised called number by the same trie the rate and route tables use, cached in the API and invalidated through Redis. The match is taken when the CDR is created, right after normalisation, so even a rejected call carries it, and the three columns (`area_prefix`, `area_description`, `operator_name`) are written with the CDR rather than resolved at display time: a later edit to the table never rewrites history, and the backfill endpoint is there to relabel on purpose. Prefixes are unique across the table, so a number can never match two entries of the same length.

  The shipped set covers the DRC (mobile ranges per operator from the e164.com registry, which the DRC's lack of number portability makes reliable, plus the fixed line ranges) and India: all 2,598 geographic STD codes with the town or towns each serves and the state in the notes (scraped from the nriol.com statewise tables into `deploy/data/india-std-codes.csv`, which ships alongside the migration so the list can be corrected and re-imported), plus the mobile series 6, 7, 8 and 9 labelled only as "Mobile" because portability makes the series meaningless as an operator. A country level fallback per covered country catches anything the specific entries miss. Everything else is one CSV import away, and an import replaces entries with the same codes so a corrected file can simply be re-imported.

* **D-77 A rejected call says what to fix.** `reject_reason` is what the caller was told ("No route"), which is deliberately vague; `reject_step` and `reject_detail` are what an operator needs, written on the same CDR at every rejection point: the IP and transport that matched no customer, the number that could not be normalised and the options it was normalised with, the deck that had no rate, the balance against the reservation it could not cover, and for routing either the prefix that matched nothing or every carrier on the matching route with the reason it was skipped, carrying the two rates behind a lossless or negative margin skip. The detail is operator data: it names costs and carriers, so it stays out of the customer and carrier CSV views and never reaches the caller, who still gets the plain SIP reason. It also lands in `sbc_reject_detail` for the dialplan and in the rejection log line.

  Each rejection point owns its own detail rather than the step guessing one: the authorize step alone rejects for six different reasons (unknown address, suspended customer, customer concurrency, customer CPS, global concurrency, global CPS), and the first version of this attached the address text to all of them, which read as a whitelist failure on a call that was in fact a limit rejection from a known customer. The limits are also the two most confused settings on the system, so their details name the setting that was hit with its counter and say that the other limit is separate, and the global ones say the customer was within its own limit.

* **D-78 The hourly roll-up and the capture feed fail loudly.** `cdr_hourly_stats` was recomputed by one statement that deleted the stale hours in a `WITH` clause and inserted the fresh ones in the same command. Postgres gives no ordering between a data modifying CTE and the rest of the statement, so the insert raced the delete and every pass failed on the unique key: the table froze on 2026-09-23 and the dashboard said "no calls yet today" while the CDR list showed the calls, because the dashboard reads the roll-up and the CDR list reads `cdrs`. The pass now resolves the stale hours first and runs the delete and the insert in order inside one transaction, the worker records its last success and last error for `/system/status` and a `sbc_reports_rollup_last_success_timestamp_seconds` gauge, and a failure logs at error level rather than warn, because a warning once a minute is what let this sit unnoticed for three weeks.

  The same day showed the matching failure in SIP capture: heplify-server gives up permanently when the database refuses its first connection and then silently discards every packet it receives. `depends_on` does not help, because after a host reboot Docker starts containers by restart policy with no ordering at all, which is exactly what happened. It now waits for the database port before it starts.

  Capture retention was working as configured, 30 days, but the partitions were not: heplify cuts SIP captures every two hours and QoS every six by default, and each partition carries 13 indexes, so 30 days came to about 1,900 tables and 26,000 relations. One query over three capture tables then needed more lock slots than the whole server had, which is the failure that surfaced this. The partitions are now one per day, which for this volume is a few thousand rows each and prunes on `create_date` exactly as well, and the capture database runs with `max_locks_per_transaction=256` so the old fine grained partitions can age out without anything failing in the meantime. heplify skips a day that already has partitions, so the change needed no migration: the old two hour ones simply expire.

* **D-79 The watchdog mails an all clear, and shouts once when it is not.** A systemd timer runs `sbc-watchdog` on the host every five minutes. It checks the systemd units, every container of the live compose project, each dependency behind `/readyz`, the carrier gateways and the roll-up freshness from `/metrics`, the nftables table with its sets, SIP capture against the calls actually handled, disk, load and memory, and the certificate expiry. It runs on the host rather than inside a container on purpose: a watchdog that dies with the stack it watches is worth nothing, and from the host it can also see systemd, nftables and the disk.

  A problem raises one alert the moment it appears, repeats at most every thirty minutes while it lasts, and is followed by a recovery notice; the state lives in `/var/lib/supersbc/watchdog.json` so a restart never floods the inbox. The all clear goes out once a day with every check and the last 24 hours of traffic, and the subject line always carries the name and the public address, so a phone shows what is wrong and where before the mail is opened. A reboot between two passes alerts by itself even when every service came back, because three unplanned reboots in two days is the kind of thing a quiet recovery hides.

  The SMTP password is read from `.env.live`, which is git ignored, and never passed as an argument, so it cannot surface in the process list, the journal or a crash log.

  Planned maintenance opens a window with `make live-watchdog-mute FOR=2h WHY="..."`, which holds back alerts and recovery notices without stopping the checks. The problems seen inside a window are deliberately not remembered, so whatever is still broken when it closes counts as new and alerts on the very next pass rather than waiting for the repeat timer: a window can delay an alert, never swallow it. The daily report still goes out and carries a banner saying a window is open and until when, so a quiet inbox is never ambiguous.

* **D-80 The node has a name and a certificate browsers trust.** The host answers to `sbc.softautonomi.com`, and the UI is served on 443 with a Let's Encrypt certificate instead of a self signed one on 8443. 8080 and 8443 stay published so nothing that already points at them breaks.

  Renewal runs through the ACME webroot that nginx serves from a bind mount, not the standalone server, so a renewal never needs the web server stopped. The deploy hook distributes the result: the chain and key for nginx, and a concatenated `agent.pem` for FreeSWITCH so SIP TLS and WSS present the same certificate as the UI, then reloads both. The certificate is in the watchdog's checks, so it reports the days left in every all clear and alerts three weeks before expiry rather than on the morning it breaks.

  The browser tab carries a mark that matches the one in the sidebar, the forwarded call glyph on the brand indigo, as an SVG with a three size `.ico` behind it for older clients, plus the touch and manifest icons so an installed window is branded too.

* **D-81 Brute force and scanners, now that the UI has a public name.** The VoIP side was already the strong half: SIP and RTP reach FreeSWITCH only from the customer and carrier sets, everything else to the host is dropped, per source packet meters sit in front of that, and an unauthorised INVITE counts towards an automatic ban. Putting the UI on a public name changed the web side, which a scanner finds within hours of the DNS record appearing.

  nginx now carries three rate limit zones per source address, strict for the three doors worth guessing at (sign in, password reset, second factor), generous for the rest of the API and for the application itself, with a connection cap. Probe paths no part of this application serves, the WordPress and phpMyAdmin and `.env` sweeps, are answered with 444: the connection closes with no response, which costs the scanner a round trip and keeps the log readable.

  Behind that the API counts failed sign ins, password resets, second factors and API keys per address, and crossing the threshold puts the address on the same ban list the SIP scanner protection uses, so the kernel drops it. Three addresses are never banned automatically, because a ban is dropped before the rules that let signalling in: an address belonging to a customer or a carrier, an address inside our own networks, and this node's own address. Each of those is recorded as a notification for an operator instead, since a customer hammering the login is a support call, not an attack.

  Attribution had to be fixed for any of this to hold: `X-Forwarded-For` was believed from anyone and the leftmost entry was taken, so an attacker could rotate the header to slip past the per address throttle, or name a third party and have them banned. It is now believed only from our own proxies, and only its rightmost entry, which is the address our nginx actually saw. The per address login ceiling came down from 100 failures in fifteen minutes to 25 at the same time.

* **D-82 A public site in front of the portal.** `sbc.softautonomi.com` now opens a marketing site that anyone can read: an overview, the full capability list, a security page and a contact page, with a log in button on every one of them. The portal moved from `/` to `/dashboard` so the public site owns the root, which is what a visitor and a search engine expect; the post login redirect, the sidebar and the browser tests moved with it, and a deep link to any portal page still goes through the login screen and returns to where it was going.

  It is the same React application rather than a second site: one build, one certificate, one deployment, and the public pages use the portal's own components and tokens, so the two halves cannot drift apart visually. Everything the pages claim is a feature that exists on a screen or an endpoint, and the numbers quoted are facts from the system rather than marketing figures. The contact details and the product wording live in `web/src/site.config.ts`, so they are changed in one file.
* **D-83 The carrier leg offers the caller's codec first.** The carrier leg used to offer the intersection of the two allowed lists in the carrier's order, so a G.729 only caller became G.729 in and PCMA out and FreeSWITCH asked `mod_g729` for an encoder it does not have ("This codec is only usable in passthrough mode", then "Codec G.729 encoder error" and a dropped call). Any codec the caller actually offered (`ep_codec_string`, sent to the API as `offered_codecs`) and both sides allow now leads the carrier's list, so the carrier answers with the codec already on the customer leg and the legs relay instead of transcode. The carrier order still decides for everything the caller did not offer.
* **D-84 Smart media mode.** `media_mode = smart` on a customer or a carrier means "proxy unless we have to anchor": if a codec the caller offered is allowed by both the customer and the carrier, the attempt is proxied (RTP relayed untouched, no decode and re-encode, the endpoints agree on the codec between themselves), otherwise it falls back to `anchor`, which is the only mode that can bridge two different codecs. Resolved per attempt in `ResolveMediaMode`, because the answer depends on the carrier. `absolute_codec_string` is only set on the carrier leg when the call is anchored; in proxy and bypass the SDP passes through and pinning a list there would be a lie. Smart calls carry the proxy caveats of D-56 (no RTP statistics, no transcoding, no inband DTMF interworking) whenever they resolve to proxy, so leave a customer on `anchor` when those matter.
