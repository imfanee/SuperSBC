# SuperSBC administrator guide

For the people who run the box: how the pieces fit, how to configure, secure, monitor, back up, upgrade and repair a SuperSBC installation. The [installation guide](INSTALLATION.md) gets you to a running system; this guide is for everything after. The [user guide](USER_GUIDE.md) covers the UI.

## 1. How it works in one page

```
customer ──SIP/RTP──▶ FreeSWITCH (external-ingress 5060/5061) ──Lua──▶ sbc-api /internal/v1/call/setup
                                   │                                    (authorise by IP, limits, normalise,
                                   │                                     rate, reserve money, route)
                                   ▼                                    ◀── decision: reject or dial [carriers]
                      FreeSWITCH (external-egress 5080/5081) ──SIP/RTP──▶ carrier 1, carrier 2, ...
                                   │
                                   └── hangup ──▶ sbc-api /internal/v1/call/cdr (bill once, release reservation)
```

* **FreeSWITCH** owns SIP and media. The Lua script asks the API what to do with every INVITE and executes the answer (reject with a code, or dial carriers in order with failover). If the API does not answer within 2 seconds the call is rejected (`503 SBC internal error`): the SBC fails closed, it never gives away free calls.
* **sbc-api** (Go) is stateless. Postgres is the system of record (customers, rates, routes, CDRs, ledger); Redis holds counters and caches. It also renders FreeSWITCH gateways and access lists from the database and reloads them.
* **Money**: every call reserves five minutes at setup and is billed exactly once at hangup, inside one database transaction, from ledger entries. Balances are derived from the ledger and `make reconcile` proves it.
* Details: [ARCHITECTURE.md](ARCHITECTURE.md), [CALL_FLOW.md](CALL_FLOW.md), [BILLING.md](BILLING.md); every design decision and its reason is in [DECISIONS.md](DECISIONS.md).

## 2. Environments and files

| | Development | Live |
|---|---|---|
| Compose project | `supersbc` (`docker compose ...`) | `supersbc-live` (`make live-*`, or the `LIVE` variable in the Makefile) |
| Environment file | `.env` | `.env.live` (chmod 600, contains all secrets) |
| Network | bridge 172.28.0.0/24, ports on loopback | bridge 172.29.0.0/24; FreeSWITCH on the host network |
| Data | volumes `supersbc_*` | volumes `supersbc-live_*`, backups in `backups/live`, ban export in `deploy/live/state` |
| TLS | `freeswitch/tls` (self signed) | `deploy/live/tls` (`server.crt`/`server.key` for nginx, `agent.pem`/`cafile.pem` for FreeSWITCH) |

Containers: `supersbc-live-{api,web,freeswitch,postgres,redis}-1` (live), `supersbc-{...}-1` (dev). Everything is configured through environment variables: see [CONFIGURATION.md](CONFIGURATION.md).

## 3. Users, roles and API access

* Roles: `viewer` (read), `operator` (read and write business data), `admin` (everything, including users, API keys, settings, profile restarts).
* The bootstrap admin (`SBC_BOOTSTRAP_ADMIN_EMAIL`) is created when the user table is empty. Change its password at once, enable TOTP, create named users, and keep the bootstrap account only as a break-glass login.
* Passwords: argon2id; repeated failed logins per account or per address are throttled (429) for a while. Resets are one time links generated by an admin (no e-mail is sent).
* API keys (System > API keys, admin only) carry a role and are sent as `Authorization: Bearer sbc_...`; they bypass CSRF and are meant for integrations (billing systems, provisioning). Every key use is logged with the key name.
* Sessions are httpOnly cookies (Secure on live), 15 minute access token with a 7 day refresh; CSRF protection with a double submit token on every state changing request.
* The audit log (System > Audit log) records every change with the actor, the before and after values and the source address. It cannot be edited through the API.

## 4. Network and security

### 4.1 Firewall (live)

`deploy/live/nftables.conf` is the whole host firewall, applied and persisted by `make live-firewall`. It allows: ssh, 8080/8443 (web), 5060 UDP/TCP and 5061 TCP (customers), RTP 16384 to 32768, 5080/5081 from the `carriers` set only; everything else to the host is dropped (ESL, the internal API, Postgres and Redis are only reachable from the docker bridges and loopback). It also:

* drops everything from the `banned` set, which `make live-ban-timer` keeps equal to the SBC ban list (System > Banned IPs) every 30 seconds;
* rate limits SIP per source (200 UDP packets per second, 30 new TCP connections per second) so a flood is dropped by the kernel before FreeSWITCH parses it.

Carrier addresses: list them in `deploy/live/carriers.nft` (included by the ruleset, git-ignored) and run `make live-firewall`; `nft list set inet sbc carriers` shows what is active. Note that responses to calls the SBC originates are always accepted (connection tracking), so a missing carrier address only breaks what the carrier initiates: its OPTIONS pings and inbound calls. Check what is being dropped: `nft list chain inet sbc input` (the counters) and `nft list set inet sbc banned`.

### 4.2 Customer authentication and scanner protection

Customers are authenticated by source address (and optionally port and transport); there is no SIP digest authentication by design (wholesale). Unknown addresses get `403 IP not authorized`; after `SBC_BAN_THRESHOLD` (20) of those in `SBC_BAN_WINDOW` (5 min) the address is banned for `SBC_BAN_DURATION` (1 h): FreeSWITCH's ACL answers `403 Forbidden` without waking the API, the host firewall drops the packets, and the ban is visible and revocable in System > Banned IPs. `SBC_ACL_MODE=strict` makes FreeSWITCH drop unknown addresses even before counting (use when you never need to see them in the CDRs).

### 4.3 SIP TLS and SRTP

TLS listeners are on by default (5061 customers, 5081 carriers) with the certificate in the TLS directory. Per customer: `require_tls` refuses UDP/TCP; per customer and carrier `srtp_mode` off/optional/mandatory. FreeSWITCH bridges SRTP to RTP and back, so a customer can be SRTP while the carrier is plain.

Client certificates (mutual TLS): set `SBC_FS_TLS_VERIFY_POLICY=subjects_in`, append the CA that issues customer certificates to `cafile.pem` (after our own chain), fill each customer's "TLS client certificate subject" (CN or SAN), and restart the ingress profile (System page or `POST /api/v1/system/profiles/external-ingress/restart`; it drops calls in progress on that profile). Connections with an unknown certificate fail at the handshake. FreeSWITCH cannot attribute a call to a customer by certificate; the address still identifies the customer (D-67).

### 4.4 Topology hiding and headers

The SBC presents its own address in From, Contact, Via and SDP on both sides; customer headers (X-headers, P-Asserted-Identity, Remote-Party-ID) are stripped on egress unless a header rule passes a named header through; identity headers can never be passed through. Privacy requests are honoured per carrier (`privacy_mode`). STIR/SHAKEN Identity headers are verified per customer when asked (`stir_mode`) and forwarded when valid.

### 4.5 Web

nginx terminates TLS on 8443 (8080 redirects), adds a strict Content-Security-Policy, `X-Frame-Options: DENY`, `nosniff` and a referrer policy; the API adds the same headers. Put a CA issued certificate in `deploy/live/tls` before giving the URL to colleagues. An OWASP ASVS level 1 walkthrough is in [SECURITY.md](SECURITY.md).

## 5. Capacity and tuning

* One box handles about 25 to 40 CPS per modern core with media relay and no transcoding; transcoding costs about one core per 30 to 40 concurrent calls. The 4 vCPU pilot VM sustains 25 CPS ([PERFORMANCE.md](PERFORMANCE.md)).
* `SBC_FS_MAX_SESSIONS` (two per call) and `SBC_FS_SESSIONS_PER_SECOND` (two per CPS) are FreeSWITCH's hard caps; `SBC_ROUTING_GLOBAL_MAX_CHANNELS` and `_MAX_CPS` are the SBC's admission caps and give customers a clean `480`/`503` instead of FreeSWITCH refusing INVITEs.
* File descriptors: four per call; the compose files set `nofile` to 65536.
* Postgres: `synchronous_commit` stays on (money). On slow disks put the volume on SSD; the pool is 50 connections.
* Redis is negligible. The API uses about half a core at 50 CPS.

## 6. Monitoring

* `GET /readyz` (loopback 28080 on live, or `https://<ip>:8443/readyz`): `ready` plus per dependency checks; use it for your external monitoring.
* `GET /metrics` (Prometheus): calls by disposition, rejections by reason, per carrier attempts and ASR, PDD histograms, concurrent calls and CPS gauges, revenue and cost counters, bans, STIR results, media modes, gateway states. `make live-monitoring` starts Prometheus and Grafana with the bundled dashboard at `https://<ip>:8443/grafana/`.
* Logs: JSON lines with `call_uuid`, `customer`, `carrier`, `step`, `code`. `make live-logs` follows all containers; `docker logs supersbc-live-api-1 | jq 'select(.call_uuid=="...")'` follows one call. FreeSWITCH logs are in the `fslogs` volume.
* SIP capture: the built-in SIP trace (System page) for a few minutes; HOMER (`make homer-up` plus `SBC_FS_HEP_SERVER`) for permanent capture and search by Call-ID.
* Alerts worth having: `ready` false for more than a minute; any gateway `DOWN`; rejection rate above a few percent; ASR of a carrier below 30 percent; reconcile mismatches above 0; disk above 80 percent.

## 7. Backups and restore

Backups: `make live-backup` (immediate `pg_dump -Fc` into `backups/live`) and the `backup` compose profile (nightly at 02:30 UTC, `BACKUP_KEEP_DAYS` retention). Copy `backups/live`, `.env.live` and `deploy/live/tls` off the box; the database plus those files is everything.

Restore on a fresh box:

```bash
git clone ... /root/supersbc && cd /root/supersbc
cp <saved .env.live> .env.live && cp <saved tls files> deploy/live/tls/
make live-up && make live-down            # creates the volumes and the empty database
$(LIVE) up -d postgres
$(LIVE) exec -T postgres pg_restore -U supersbc -d supersbc --clean --if-exists < backups/live/supersbc-<stamp>.dump
make live-up && make live-reconcile
```

CDRs that FreeSWITCH could not deliver while the API was down are spooled and re-posted with `make live-replay-cdrs` (idempotent).

## 8. Routine operations

| Task | How |
|---|---|
| Status | `make live-ps`, `curl -sk https://127.0.0.1:8443/readyz` |
| Restart one service | `$(LIVE) restart api` (no calls dropped); `... restart freeswitch` drops calls |
| Reload a carrier gateway | automatic on save; by hand `fs_cli -x "sofia profile external-egress rescan"` |
| Console | `docker exec -it supersbc-live-freeswitch-1 fs_cli -H 172.29.0.1 -p "$SBC_ESL_PASSWORD"` |
| Prove the books | `make live-reconcile` (0 mismatches expected) |
| Ban / unban | System > Banned IPs, or the API; the firewall follows within 30 s |
| Rotate the ESL or internal secret | change in `.env.live`, `make live-up` (restarts FreeSWITCH) |
| Rotate the JWT secret | change and `$(LIVE) restart api`; every user logs in again |
| Certificate renewal | replace `server.crt`/`server.key`, `deploy/live/init.sh`, `make live-up` |
| Disk | CDRs grow about 2 KB per call; `cdr_hourly_stats` is small; prune old CDRs with a scheduled `DELETE FROM cdrs WHERE start_time < now() - interval '13 months'` only after exporting them |

## 9. Upgrades and rollback

`git pull` then `make live-up`: images are rebuilt, migrations run at API start, FreeSWITCH is recreated only when its configuration changed (dropping calls). Take `make live-backup` first. Rolling back the code is `git checkout <previous tag>` and `make live-up`; rolling back a migration is `sbc-api migrate-down` inside the container and is only safe for the migrations noted as reversible in the release notes (all migrations so far add columns or tables and are reversible).
